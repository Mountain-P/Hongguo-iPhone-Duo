# 0.16.2 / build 52 離線下載取源恢復

## 實際故障

2026-11-14 使用獨立 iPhone Duo 模擬器 App，從 `368c761` 的正式下載程式碼重現：

| 《幸得重生不負青梅》 | 結果 |
| --- | --- |
| 第 20 集 | 完成，5,373,857 bytes |
| 第 21 集 | 完成，4,232,695 bytes |
| 第 22 集 | `EMPTY_RESPONSE`，0 bytes，顯示「來源未回傳影片資料，請稍後重試。」 |

這次失敗發生在下載影片之前。下載先嘗試直接 MP4；這個探測只使用主要 API。原先只有「沒有可直接儲存的明文 MP4」才會轉入完整播放取源，所以 API 空回應、逾時和暫時斷線會直接讓下載失敗。0.16.1 的播放器備援請求雖已更新，這條下載分支仍無法接上。

## 修改

- 正式下載直接使用完整播放取源，省去原本額外的直接 MP4 探測。它包含有期限、有限次數的替代主機請求，已有的寫檔器可處理明文及支援的加密 MP4。
- 完整取源若仍暫時回空資料或發生可恢復的網路錯誤，等待 1 秒再重新取同一集一次。等待可取消；拒絕與限流不重試。
- 原生 JSContext 之間共用匿名播放身分，僅留在記憶體 5 分鐘。tab 與 legacy 分開儲存；第二輪 legacy 恢復仍會要求新註冊。到期重新取得，失敗不覆蓋既有有效身分。快取只接受非零裝置／安裝 ID 與 UUID，不接受帳號、Cookie 或額外欄位。
- 將 HTTP 200 但裝置與安裝 ID 都明確為 0 的註冊回覆識別為 `REGISTRATION_UNAVAILABLE`。本次查詢立即停止重複註冊，由下載端等待 10、20、40 秒後重試同集，最多四次；等待可取消。明確拒絕與 429 不套用此恢復，其他格式錯誤也不假裝有合法身分。
- 保持原本劇集、分集、內容類型及畫質，不接受別集的模型。明確授權拒絕、限流、模型不合法及取消不會改走其他取源。
- 下載中斷後的單次重新取源也走相同恢復路徑。完整取源仍失敗時正常回報，不無限重試；暫存檔仍清理，通過完整 MP4 驗證後才加入離線片庫。
- 更新四份 JS 的原生身分快取接點、註冊回覆分類與 SHA-256 manifest；未修改簽章演算法、CDN 允許規則或加解密流程。

## 回歸測試

新增可重現舊行為的測試，修正前記錄到 6 個失敗。修正後確認空回應、逾時、連線錯誤與 503 能完成 MP4 下載；也測試下載後重新取源、取消優先、拒絕與限流停止、備援耗盡不循環、相同分集與畫質綁定。

這個工作區包含原有未提交的資源雜湊測試；該測試未納入本次提交。模擬器建置並行時，既有 `recoveryRaceDoesNotRetryAnExplicitProviderDenial` 曾出現請求數斷言失敗；單獨重跑與後續完整測試皆通過，未更動該播放競速測試或邏輯。新增延遲重試成功、延遲期間取消、重試耗盡、拒絕停止，以及跨 JSContext 共用匿名身分、快取到期、scope 隔離、拒絕額外帳號欄位、更新失敗保留有效值案例。

最終完整 `swift test` 通過 Core 620 項、AppSupport 112 項，另含零 ID 與業務拒絕的差異、只發一次註冊請求後交回等待、10/20/40 秒上限及等待取消測試。

## 模擬器實測

透過 `scripts/offline-download-qa.py` 啟動隔離的測試 App，使用正式 `NativeCatalogService.downloadOffline` 與 `OfflineDownloads`。測試不操作實機。下載後重新啟動同一個測試 App，核對片庫雜湊與保存進度，再從本機檔案解碼開頭、中間及接近結尾的畫面。

最終版本從第 1 集重新下載至第 91 集，結果如下：

| 項目 | 結果 |
| --- | --- |
| 完整下載 | 91／91 集，0 失敗 |
| 影片總大小 | 559,593,731 bytes（約 534 MiB） |
| 匿名身分註冊請求 | 全部 91 集合計 5 次 |
| 外層重新取源／延遲重試／註冊等待 | 此輪均未觸發；對應故障與取消由回歸測試覆蓋 |
| 重新啟動後片庫驗證 | 91 集檔案與雜湊通過，保存的第 2 秒進度均保留 |
| 本機影片解碼 | 91 集各取開頭、中間、近結尾，共 273 個畫面成功 |
| 重開階段取源請求 | 0；測試 provider 若被呼叫會直接報錯 |

這是實際下載後重新啟動 App 的本機檔案驗證；沒有切斷整台 Mac 網路，也不等同使用播放器 UI 播完整部或實機測試。測試使用 `file://` 影片資產；進度驗證檢查的是片庫保存值。

修正過程中，僅接上完整取源時，第 18 集仍出現 `EMPTY_RESPONSE`。隨後使用相同原生 JavaScriptCore/HTTP 取源，該集主 GET 重新回傳 18,121 bytes 的有效 1080p 模型，證明不是固定分集不可用。這促使本版加入一次有間隔的重新取源。

第二輪延遲重試曾成功救回第 1、13 集，但批次後段出現大量 `DEVICE_REGISTRATION_FAILED`，最終 23 集完成、68 集失敗。唯讀回應診斷顯示註冊 API 回 HTTP 200、100 bytes，裝置與安裝 ID 都為 0；另一輪註冊才重新回有效 ID。沒有證據可以把這個 HTTP 200 當成成功，也不能僅憑零 ID 判定具體的服務端限流規則。原本每個一次性 JSContext 都重新註冊，使批次流程頻繁依賴這個不穩定步驟，因此加入上述共用快取並取消額外直接 MP4 探測。

重跑命令：

```sh
python3 scripts/offline-download-qa.py \
  --device SIMULATOR_UUID --episodes 1 91 \
  --output build/offline-qa-new-run
```

尚未提交的 Core 修正可加 `--working-tree`。預設使用提交的 HEAD；它只重設獨立的 `tw.mountainp.hongguo.offlinebatchqa`，保留一般 App。QA 副本在取源恢復與延遲重試處加入安全紀錄，不修改判斷或請求內容。若由 runner 啟動模擬器，結束後會關閉。證據僅保存集數、位元組數、耗時、錯誤代碼與本機解碼結果，不保存金鑰、Cookie、帳號或簽名網址。測試媒體留在該模擬器 App 私有片庫，未加入 Git。

本機證據：`build/offline-source-recovery-0.16.2/`；最終完整批次為 `cooldown-simulator/`，內含 `summary.json`、下載與重開紀錄。測試 runner 已正常結束並關閉該模擬器。模擬器的實際網路下載與解碼不等於所有來源或實機網路都不會失敗；API 與 CDN 若持續不可用，仍可能需要稍後重試。
