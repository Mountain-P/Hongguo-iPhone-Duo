# 0.17.1 / build 58 播放修復驗證

日期：2026-11-24（Asia/Taipei）。修復基線為中繼分支 `d623465`。

## 問題與對照

0.17.0 安裝後使用者回報「來源未回傳影片資料」。相同原始碼的 iPhone Duo 模擬器，以正式 AppModel、PlayerModel、NativeCatalogService 播放《幸得重生不負青梅》第 20 集，在 0 秒重現相同錯誤；macOS 原生取源探針也失敗。

- 舊請求與簽章：取源失敗。
- 只將 Medusa 第 21 欄位由 377 改為 312：相同樣本仍失敗。
- 同時採用目前 7.4.5.32 的 preload 請求、主機及欄位 312：取得 1080p HEVC，macOS 漸進式播放探針準備 2.12 秒、首個解碼影格 2.38 秒。

因此本次修復需要更新播放請求與簽章的組合；沒有把單一欄位或網路速度當成所有情況的唯一原因。

參考 [N3urda/hongguoTV 的實測調查](https://github.com/N3urda/hongguoTV/blob/ef328f3a3dc28479d90608a507996136672cf946/docs/research/2026-11-23-issue102-nonweb-playback.md) 與同一提交的 MobilePlayback/V5Constants。沒有加入官方 SDK、遠端執行 JavaScript 或第三種取源模式。

## 實作範圍

- 手機直連改用目前的播放請求與簽章，保留相同分集與內容類型。
- 空 HTTP 200 可在既有時間預算內，以相同匿名身分向第二個官方主機重新簽署請求。401、403、429 與業務拒絕仍停止。
- 模型只提供 ByteVC2 時，依該模型提供的 VOD 介面要求 H.264/HEVC。最多兩個編碼選項；保留其他 query bytes，核對影片 ID、完整時長、原畫質門檻及加密資訊。
- Node 與 iOS 兩份播放模組同步，更新 14 個 JavaScript 的 SHA-256 清單。伺服器原始碼更新不等於已部署家中服務。
- 帳號、搜尋、片庫及中繼選項保留。

## 自動回歸

- Swift Core：639 項／64 suites 通過。
- Swift AppSupport：112 項／7 suites 通過。
- Node：32 項通過。
- 使用上游公開合成身份的完整 wire 向量，在 JavaScriptCore 與 Node 驗證 Medusa/Helios 輸出；不是只檢查欄位字面值。
- 編碼協商涵蓋同集成功、錯集、較短影片、403、不受信任媒體域名、仍無兼容編碼、低於原畫質及缺少加密資訊。

第一次完整測試在同時建置時出現一項既有 recovery race 計時測試失敗；該測試單獨重跑及最後完整回歸均通過，正式串流競速邏輯沒有改動。

## 實網與平台範圍

另抽測三個上游問題樣本，兩個直接取得 1080p HEVC；《全球死考》第六季第 153 集先重現 ByteVC2 不兼容，加入模型提供的編碼協商後取得同集 1080p H.265。這三個樣本是取源驗證，不能當作完整集播放驗收。

完整播放使用隔離的 iPhone Duo / iOS 27.2 模擬器、正式 PlayerScreen/PlayerModel，只有 App 入口替換為自動驗收入口；無中繼口令，必須走手機原生取源與實際 AVFoundation 解碼。測試靜音，並以 AVPlayerItemVideoOutput 確認解碼影格。

最終版本三集（第 20～22 集）以 2 倍速完整播放、正常自動換集；累計 114.09 秒，無量測到的停頓或播放器重載，擷取 924 個實際解碼影格。各集起播為 6.78、0.22、0.75 秒。這是該次網路與模擬器的結果，不是所有網路都無緩衝的保證。先前一輪同樣三集完整播放，在第三集片尾量測到 0.66 秒停頓。

另一部劇（series ID `7701935931787316286`）第 2 集的 macOS 完整音視訊解碼通過：103.44 秒、2,585 影片影格、1,035 音訊 buffer，1080p HEVC。這是原生管線與 macOS 解碼器驗證，不能替代 iPhone 喇叭驗收。

實機 Release 包為 0.17.1 / build 58；簽署、配對手機與原 Team/Bundle ID 相符，21 個 App 內播放資源與原始碼逐檔一致。手機已覆蓋安裝並讀回確認為 0.17.1 / build 58；解鎖後 devicectl 啟動成功。沒有卸載或清除使用者資料，不使用手機操作影片測試。所有模擬器已關閉。
